## Blocking findings

### F1 — Primary consumer integration is broken/stale (High, blocking)

**Evidence.** dicom-curate `package.json` pins `"dicom-synth": "^0.1.0"` (devDependencies). Its conformance suite and baseline tooling import `SYNTHETIC_FIXTURES`, `SyntheticCtVariant`, and `writeSyntheticFixturesToDir` (`conformance/helpers.ts:6-10`, `scripts/update-conformance-baselines.ts:19-27`), with committed baselines keyed to the old variant names (`minimal-ct-0`, `valid-uid-ct-0`, `vendor-warnings-ct-0`). Those exports were removed from dicom-synth in `d5c5911` ("replace fixed fixture catalogue with schema-driven dataset generation"); the PR C rename (`*-ct` → `*-image`) also renamed the variants. The public-fixtures API dicom-curate uses (`defaultPublicCasesPath`, `loadCaseById`, `fetchPublicCaseToCache`) is still exported and signature-compatible.

**Consequence.** Everything built since 0.1.0 — schema/parametric specs, grouping, describe, large files, violations, tree capture — has never been exercised by the system it exists to serve. Upgrading dicom-curate is a breaking migration, and its conformance model treats any change to generated bytes as a baseline-regeneration event (`conformance/README.md:71`), so the upgrade is deliberate work, not a version bump.

**Recommended next steps.**
1. Decide the migration shape: (a) dicom-curate replaces the catalogue imports with a small pinned `DatasetSpec` (+ seed/uidSalt) and `writeCollectionFromSpec` — preferred, keeps dicom-synth minimal; or (b) dicom-synth ships a thin named-preset helper (e.g. `CONFORMANCE_PRESETS`) as a stable convenience surface.
2. Do the dicom-curate migration (bump to ^1/^2, regenerate dciodvfy baselines, rename variants), and treat it as the acceptance test for the v1 API.
3. **Gate PR O on this**: do not drop the "APIs may change" banner (declare v2 stability) until the primary consumer compiles and passes conformance against the new API.

### F2 — CLI tests silently skip in CI and at the release gate (High — ✅ resolved, PR #22 2026-07-11)

> **Resolved:** both workflows now build before testing; `test/helpers/cliBuild.ts` throws under `CI` when `dist/esm` is missing, so the skip can never be silent again. Original finding retained below.

**Evidence.** `test/cli.test.ts`, `test/cli-generate.test.ts`, `test/cli-describe.test.ts` guard every test with `it.skipIf(!hasBuild)` where `hasBuild = existsSync('dist/esm/index.js')`; the bins import from `../dist/esm/index.js`. `dist` is gitignored. Both `.github/workflows/ci.yml` and `release.yml` run `pnpm test` **before** `pnpm build` — so on a fresh runner the entire CLI surface (≈29 tests) skips, and vitest reports success. Only the local pre-push hook (build → test) runs them; locally they also test a possibly **stale** dist rather than current source.

**Recommended next steps.**
1. Reorder both workflows: Build before Test (one-line change each).
2. Make the skip loud: in CI (`process.env.CI`), fail instead of skipping when `dist` is missing (e.g. `if (process.env.CI && !hasBuild) throw`).
3. Optional: have the CLI suites depend on a fresh build locally too (pre-test build, or a `globalSetup` that builds once), so they can't validate stale output.

### F4 — Private/vendor tags cannot be generated (Medium, blocking — elevated 2026-07-11)

`applyTagOverrides` (`generator.ts:74-91`) resolves hex tags through dcmjs's `nameMap`; private tags (odd group, e.g. `00091001`) aren't in the dictionary → `console.warn` + skip. Strategy W5 (quarantine review, "preserve vendor-specific private tags") and dicom-curate's real private-tag logic (`deidentifyPS315E.ts`, `curateDict.ts`, nested-sequence retention) therefore cannot be fed synthetic private blocks.

**Recommended next steps.** Pre-release PR (**PR Q** in plan.md — not part of the CI PR): support raw private elements — hex tag + explicit VR written into the denaturalised dict, including private creator blocks and nested private sequences; validate hex tags at spec level (closes the F7(a) warn-and-skip path for the same route).

### F5 — No browser/in-memory surface for medex (Medium, blocking — elevated 2026-07-11)

medex is a browser app; it feeds dicom-curate `File[]` (`inputType: 'files'`) and mocks `FileSystemDirectoryHandle`s, currently from one checked-in real DICOM + zero-filled blobs. dicom-synth imports `node:fs`/`node:crypto` at module top level in every path, so even the in-memory generator can't load in a browser/jsdom bundle.

**Recommended next steps.** Pre-release PR (**PR R** in plan.md — not part of the CI PR): (1) split a browser-safe entry point (in-memory generation is already bufferised — the blockers are the fs/crypto imports and `writeCollectionFromSpec` living in the same module graph); (2) a `File[]`/mock-directory-handle adaptor for the medex harness; (3) until it lands, document that the surface is Node-only.

## Non-blocking findings

### Capability gaps vs the strategy docs and consumers

**F13 — Correlated CSV sidecars (Low–Med).** W2 (two-pass CSV mapping) and both consumers' CSV flows need `CURR_ID,NEW_ID,DATE_OFFSET`-style CSVs consistent with generated identifiers. `non-dicom` `content` can hold a hand-written CSV, but nothing generates one from the dataset's own (templated/hashed) identifiers. *Next step:* roadmap a small manifest→CSV helper or document the recipe (the emitted spec contains everything needed).

**F14 — Compressed transfer syntaxes (Low).** Only Explicit/Implicit VR LE are supported; dicom-curate preserves incoming `TransferSyntaxUID` and carries a full UID registry, but no fixture exercises JPEG*/RLE/deflated paths. Already listed in README Future development — fine for v1; worth keeping high on the post-v1 list given curate's registry is untested.

**F15 — Node version matrix (Low).** `engines: >=20` is claimed; CI tests only Node 24.13.1 on ubuntu. *Next step:* CI matrix `[20, 22, 24]` (cheap; suite runs in ~3s).

**W1–W7 fit summary:** W1 ✅ (presets, violations, tags) · W2 ◐ (files yes, CSV sidecar manual — F13) · W3 ✅ (parametric scale, streamed ≤50 GB, sized non-DICOM) · W4 ◐ (pathQuirks yes; browser `File[]` no — F5) · W5 ✗ (private tags — F4) · W6 ✅ (tree/layout/manifest) · W7 ◐ (public-fixture fetch layer exists but catalogues only 2 pydicom cases; the fuller corpus intentionally lives with dicom-curate's conformance harness per strategy §4.5.3).

### Correctness / robustness (minor)

**F6 — Unknown spec fields pass silently (Medium; already planned).** `validateEntry` uses per-type deny-lists, so a typo (`targetSizeKB`, `frame`) is ignored and yields a default 1×1 image. This is exactly PR O step 4 (TYPE_CAPABILITIES → per-type allow-lists); this review confirms it's worth doing and suggests also rejecting unknown **top-level** `DatasetSpec`/`ParametricSpec` keys.

**F7 — Silent-degrade paths (Low–Med).** (a) Unknown hex tag → warn + skip (`generator.ts:85`) — with F4 unresolved this is the only route users will hit; prefer failing at validation (the dictionary is available). (b) `applyTagLevel` catch → warn and return the **original, unviolated** buffer (`violations.ts:58-63`) — a fixture consumer asked for a violated file and silently gets a clean one; since tag-level violations always run on a freshly generated valid buffer, the catch is effectively dead — prefer throwing. (c) Library warnings go to `console.warn` with no way to silence/capture; acceptable for v1, note for the API surface.

**F8 — Large-file happy path env-gated (Medium).** `writeLargeImageFile`'s success path (`streamWrite.ts:301-308`) runs only under `DICOM_SYNTH_LARGE_TEST`; `streamLargeImage` is well covered at KB scale via ceiling overrides. *Next steps:* a scheduled (nightly/weekly) or manual workflow job that sets the env var and writes one real >512 MB file; plus a small unit asserting `writeLargeImageFile` forwards spec fields (it currently drops none, but nothing pins that).

### Minimality / DRY / KISS (Low)

- **F9 — dead code:** `writeDicomdirFile` (`dicomdir.ts:42`) is exported from its module but absent from `src/index.ts` and unused outside its own test — remove or export deliberately.
- **F10 — DRY nits:** duplicate hex→keyword map builders (`generator.ts:53` `buildTagToKeyword` vs `describe.ts:98` `buildHexToKeyword`); `HEX_TAG_RE` defined in both `validate.ts:77` (exported) and `describe.ts:37`; `LargeImageSpec` (streamWrite) near-duplicates `LargeFileSpec` (schema) with divergent field support (`tags` only on the schema type — `writeLargeImageFile` cannot apply tags while the collection path can); `seededStream(seed, offset, a, b)` is only ever called as `(seed, PARAMETRIC_STREAM_OFFSET, 0, 0)` — the `a`/`b` generality is unused. All are small; homed in **PR S** (simplification pass + architecture artefacts, added to plan.md 2026-07-12) rather than PR O.
- Otherwise the codebase is commendably minimal: no runtime deps beyond the dcmjs peer, clean layering (generate → plan → materialise → write), and validation/limits shared from one place.

### Docs (Low, F12)

- `docs/parametric.md:30` says frequency is drawn "per file across the whole dataset"; the code's denominator excludes large-image members (`parametric.ts:60` counts only `fileCount`).
- `docs/describe.md` doesn't note that default `preserveUids` makes the emitted spec grow linearly with file count (per-file hashed SOP UID arrays; `sizeTolerance` cannot fold them) — worth one sentence recommending `--no-preserve-uids` + `sizeTolerance` (or `--gzip`) for very large trees.
- `docs/schema-reference.md:12-19` `DatasetSpec` snippet omits `pathQuirks` (documented later on the page).
- `docs/cli.md` `--uid-salt <hex>` implies hex; any non-empty string is accepted. `--large-file` silently ignores `--out`/`--emit-spec`.

### Infrastructure (Low, F11)

- `data/public-cases.json` URLs point at pydicom's mutable `main` branch. The sha256 pin makes drift loud (by design), but pinning URLs to a commit SHA avoids gratuitous breaks. One-line metadata edit.

## Known/accepted limitations (verified as documented — no action)

- describe skips large (>512 MB) **implicit-VR** files and headers >~2 MB (documented, `docs/describe.md:52`); >50 GB files skipped.
- Encapsulated >4 GB large files carry zero (non-conformant) pixel content — documented.
- pathQuirks are POSIX-writable only — documented with rationale.
- `uidSalt` recorded in emitted specs enables dictionary-confirmation of a *known* original UID (inherent to deterministic hashing); originals remain unrecoverable.
